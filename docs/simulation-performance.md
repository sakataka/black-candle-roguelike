# シミュレーションの性能改善（2026-10-05）

## 目的と比較基準

レベルデザインで職業・設定・灰灯院の育ち具合を並べるバッチを速くし、同じseedから同じ判断・乱数・結果を得られる状態を保つ。目標は、直近の常駐ワーカー導入後からさらに約2倍。ゲームバランス、依存関係、既定の並列数は変更しない。

比較元は `b204123`。`1b2e480` に含まれる常駐ワーカーと数値座標索引の改善、および依存更新後の状態を基準にした。前回の記録の24.7秒→7.2秒は今回の比較値に混ぜず、現在の環境で変更前を測り直す。

MacBook Pro（M4 Pro、24 GB）、Bun 1.4.2。同時にtest・build・別の計測を走らせない。変更前を別ディレクトリへ `git archive` し、同じ依存を参照する。変更前と変更後の実行順を交互に入れ替え、主な条件を3回ずつ測る。時間はCLIプロセスの起動から終了までで、結果出力とレポート保存も含む。プロファイルは別実行とする。

| 条件 | 変更前 | 変更後 | 改善倍率 | 測定回数 |
| --- | ---: | ---: | ---: | ---: |
| 標準210遠征・8並列 | 5.01秒 | 3.21秒 | 1.56倍 | 3 |
| 標準210遠征・1並列 | 27.85秒 | 14.40秒 | 1.93倍 | 3 |
| 標準210遠征・4並列 | 7.85秒 | 4.39秒 | 1.79倍 | 1 |
| 100 seed・3条件・2,100遠征・8並列 | 58.28秒 | 32.03秒 | 1.82倍 | 3 |
| アビリティ比較560遠征・8並列 | 18.17秒 | 10.42秒 | 1.74倍 | 1 |

3回の条件は中央値。4並列とアビリティ比較は単発の参考値。約2倍という目標に対し、採用した変更は1.6〜1.9倍。条件を問わず2倍は未達であり、実測以上の効果は扱わない。

標準条件は `20260504:20260533` × 全7職、上限1600手、介入なし。成長比較は `20260504:20260603` × 全7職 × baseline/fresh/late、`always-continue`（`--variant` は通常列へ比較列を足すため3列になる）。アビリティ比較は `20260504:20260508` × 全7職 × アビリティなしと各アビリティ、`always-continue`、灯守AIあり。

## 調査と採用案

初回の標準バッチの区間計測では、状態更新が約45%、AI判断が約24%、観測作成が約19%、ログが約8%。設定読込とプロセス通信は小さく、前回のワーカー改善のやり直しでは目標に届かない。

1並列・10 seed × 全7職のCPUプロファイルでは、汎用オブジェクト複製が自己時間10.7%、`structuredClone` が7.1%。地形生成の近傍・配置照合にも配列の総当たりが集中していた。関数の総時間は入れ子になるため、各割合を足して削減見込みとしない。

| 対象 | 原因と変更 | 保持する条件 |
| --- | --- | --- |
| 配置候補・遮蔽配置 | 毎回の `findIndex` と近傍の `some` を座標索引へ変更 | 配置候補の順序と重複、乱数の消費、守り手による外部 `splice` |
| 状態・観測の複製 | 固定構造の遠征情報・地形・予告・物語を専用コピーへ変更 | 入れ子の独立性、任意プロパティ、観測での未発見の熱源の除外 |
| 移動候補の評価 | 同じ目的地へ最大8回行う前向き探索を、観測ごとの逆向き距離表へ変更 | 斜め移動、罠回避、敵の扱い、塞がれた始点からの出発、同点の優先順 |
| 探索ループ | 境界・既訪問の判定後に座標を作り、探索状況のキューは数値配列へ変更 | 探索順、到達距離、フロンティアの安定した並び |
| バッチの状態更新 | 単独所有する状態を同じルールで直接更新し、全状態の毎手コピーを省略 | 通常の `applyAction` の前状態保持、更新前プレイヤー・HP・ログ用の値 |
| バッチの視界 | 地形ごとに同じ原点・半径のFOV結果を再利用 | 毎手の遮蔽差分確認、置灯・半径の変化、探索済み地形、地形交換時の解放 |
| ログ差分 | 前後の80件の重なりを値で確認し、通常経路で文字列キーと `Set` の生成を省略 | 重複の除外、ターン番号の巻戻り、先頭削除。重なりのない場合は従来手順 |
| 装備の印 | 数個の印に対する `Set`・`flatMap` の生成を省略 | 固有の印→個体の印の順序と重複除外 |

## 状態の所有と安全性

`applyAction` と `applyOwnedAction` は内部の `advanceGame` を共有する。検証・移動・戦闘・敵・灯・期限・乱数処理は一つの実装であり、シミュレーション専用のルールを持たない。

ブラウザと先読みは従来どおり `applyAction` と `observeGame` を使う。`applyOwnedAction` は、入力状態を消費し、その返り値だけを次へ渡す呼出元に限る。過去の状態や観測を保持するUIから使ってはいけない。バッチでは、直接更新されるplayerを観測時に保存し、更新前の階・手数・メッセージ配列も保持する。ログのスナップショットは以後の更新で変わらない。

比較用に `SimulationRunInput.copyState: true` を指定すると、バッチも通常の状態複製経路を通る。CLIの既定動作を変えるオプションは追加していない。経路の同値性は標準testで継続して検証する。

距離表は `WeakMap<GameObservation, ...>`、視界結果は `WeakMap<Tile[], ...>` に置く。観測や地形が不要になれば解放でき、別遠征・別configの結果を使い回さない。視界は毎手すべての地形の遮蔽を確認し、変更があれば再計算する。特定の地形変更関数だけに依存した無効化にはしていない。

## 検証

- 既存の14遠征の指紋テスト：行動、公開観測、全状態、表示意図、ログのスナップショットが一致する。
- 新規の全7職 × 介入なし/灯守AIの比較：単独所有経路と通常経路の毎手の全状態・公開観測の値を照合する。任意プロパティの挿入順は所有経路で異なるため、ここでは値と配列順を比較する。
- 全7職 × fresh/lateの14ケース：遠征結果とログを含む全評価項目を通常経路と照合する。
- 経路距離：25種類の未知・壁・罠・敵を含む盤面、4種類の通行条件、塞がれた始点と場外座標を含む12,600照合。
- 個別の回帰確認：コピーの独立性、任意プロパティ、遮蔽・置灯の変化、配置候補の重複と外部変更、ログの重複・並べ替え・先頭削除。
- バッチの全遠征結果：実行時間・プロファイル・生成時刻を除いて変更前と照合する。勝敗や到達階だけでなく、死亡原因、低HP、停滞、罠、行動回数、階別の被害、装備、任務、灯片、未返済灯火、想定表示時間、末尾ログまで比較する。

最終差分で `bun test` は142件成功、14スナップショット一致。`bun run build`（TypeScript型チェック＋Vite）も成功。上表の8,330遠征分（反復を含む）の比較は評価結果の差分0件。通常の70遠征を追加照合し、差分0件だった。

キャッシュの負荷確認として、1並列・10 seed × 全7職の最大RSSを標準timeで単発測定したところ、187.1 MiB→202.2 MiB（約15 MiB増）だった。複数ワーカー全体の最大メモリを測った値ではない。通常のCLIでの同条件の時間は7.98秒→4.45秒。ブラウザ・実機の速度は測定対象外。

## 再測定

```sh
# 標準条件。CPU負荷を抑える場合は --jobs 4、単一プロセスの比較は --jobs 1。
bun run simulate:batch -- --seeds 20260504:20260533 --turns 1600 --roles all --jobs 8 --label perf --out tmp/sim-reports/perf.json

# 100 seedで、遊び始めと終盤の条件を並べる。
bun run simulate:batch -- --seeds 20260504:20260603 --turns 1600 --roles all --jobs 8 --decision-policy always-continue --variant fresh=stage:fresh --variant late=stage:late --out tmp/sim-reports/perf-stages.json

# CPUプロファイルは並列比較の時間測定と分け、1プロセス内を測る。
bun --cpu-prof --cpu-prof-md --cpu-prof-dir=tmp/perf src/game/sim/batch.ts --seeds 20260504:20260513 --turns 1600 --roles all --jobs 1 --label profile --out tmp/sim-reports/perf-profile.json
```

今回の生データは `tmp/perf/measurements.json`、`tmp/sim-reports/benchmark-*.json`、CPUプロファイルは `tmp/perf/*.cpuprofile` と `*.md`。Git管理外のため恒久的な数値はこの文書へ残す。

## 残る候補と見送った案

- Rust/WASMへの移植：複製と反復探索の回避を先に採用した。ルールの二重実装、乱数・数値・観測・configの整合、ビルドの複雑化に対して、今回の計測だけでは移植の効果を保証できない。
- ワーカー追加や既定並列数の変更：並列数によって改善幅が違う。別の日本語修正などが進行する開発機でCPU負荷を増やす変更は行わない。
- configの永続キャッシュ：設定読込は小さい。設定変更の反映や複数configの比較を複雑にするほどの効果がない。
- ログ・観測情報の省略：比較材料そのものを削るため採用しない。
- 前景のブラウザでのFPS・描画・体感速度：今回の測定対象はシミュレーションCLI。UI・rendererは変更せず、ブラウザ性能や実機性能の改善とは扱わない。

最終の同じ70遠征のCPUプロファイルは8.33秒→4.31秒（約1.93倍、プロファイラー有効時の参考値）。汎用コピーの自己時間は10.7%→2.0%、structuredCloneは7.1%→0.7%。残る大きな単独関数は探索状況のBFS（7.2%）、視界更新（3.1%）、AIの観測索引（2.9%）などで、負担は複数箇所へ分散した。探索状況とAI索引で既知地形の格子を共用する案が次の候補だが、それだけで追加2倍になる規模ではなく、情報境界と寿命管理の変更を含む。まず別候補として実測する必要がある。

観測タイルを単独所有のバッチ内で再利用する案も試した。2,100遠征の単発では約7%短縮したが、3回の測定では効果が小さく、標準条件は3.21秒→3.45秒へ悪化した。更新する属性を絞る再試行でも大きな効果は再現できなかったため、所有期間の制約を追加する変更は採用しない。
